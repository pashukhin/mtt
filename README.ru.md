# mtt

**Исполняемая state machine для задач кодовых агентов — предохранитель между агентом и словом «done».**

> 🇬🇧 In English: [README.md](README.md)

> **Статус:** рабочая альфа — движок флоу отгружен (per-type-флоу + исполняемые, гейтящие переходы
> статуса с history, структурные команды + rollback), плюс задачи/иерархия/зависимости, база знаний
> (`mtt note`/`mtt prime`), проверяемые ссылки (`mtt ref`/`mtt check`) и скаффолдинг агент-конфигурации
> (`mtt agent`). Сборка — `mtt version`, живая поверхность — `mtt --help`.
> Мета-обход `advance`/`start`/`done` — **отложен** (одно-рёберный `status` — норма); дерево комментариев,
> текстовый поиск, `mtt-ui` и внешние адаптеры — поздние фазы. Полный план — в [DESIGN.ru.md](DESIGN.ru.md).

> **Питч — зачем тебе mtt.** У тебя уже есть Definition of Done: тесты, линт, ревью, «сначала спека — потом
> код». Он живёт прозой в AGENTS.md, в Make-таргетах, в CI. Проза агента не останавливает — она надеется.
> Агент молча пропускает всё, что не проверяется механически, и пишет «done» там, где done нет. Проблема не
> в том, что у тебя нет Definition of Done, — а в том, что его нечем принудить внутри самого трекера.
>
> mtt превращает жизненный цикл задачи в маленькую state machine, которую ты описываешь **под свой тип
> задачи** (bugfix — не refactor), и **каждый переход прогоняет твои же консольные команды как блокирующие
> гейты**: не прошли проверки — перехода нет, и статус не может соврать. Флоу — это закоммиченные данные
> репозитория, а не личные настройки; работает с любым CLI-агентом; каждый переход пишется в append-only
> историю с результатами проверок. И раз статус не врёт, когда смотришь *ты* — `mtt show` / `mtt list` /
> `mtt roadmap` — видишь честную карту: что ещё идея, что заблокировано, что в двух шагах от релиза. Одной
> фразой: **«done» — это не то, что агент объявляет, а то, что инструмент отказывается записать, пока это не
> заслужено.**
>
> **Не для всех.** mtt бесполезен, пока ты не описал флоу, — этот шаг авторинга и есть цена, а не изъян.
> Если тебе нужен просто список дел — возьми что-то легче. mtt решительно выигрывает только когда ты хочешь,
> чтобы принуждался *сам процесс* — особенно под агентами, которые пропускают всё, что не гейтится
> механически.

## Что это

`mtt` — небольшая Go CLI (`mtt add`, `mtt status`, `mtt done`, …). Ключевая идея: **config-driven per-type
flow, переходы которого запускают гейты** (консольные команды, обязанные пройти) — так агент не пометит
задачу `done`, не выполнив её Definition of Done. Вторая идея, лестница adoption: **хранилище
абстрагировано за портами**, поэтому тот же CLI работает поверх локальных файлов или твоего существующего
трекера.

- **Одиночка / zero-footprint:** дефолтный бэкенд — локальные YAML-файлы (один файл на задачу, в `.mtt/`) —
  без демона, без БД, без портов; чистые git-мержи и ревьюабельные в PR диффы.
- **Корпорация:** через адаптер направляешь mtt на уже имеющуюся связку «таск-трекер + база знаний»
  (Jira+Confluence, GitHub Issues+Wiki, …). Агенты получают тот же чистый CLI; люди остаются в родных UI.

## Зачем

`beads` хорош, но тяжёл для этой задачи: конфликтует с прочим тулингом, а его flow — плоский enum статусов.
Клин mtt — **лёгкость** и **настоящий per-type flow**, плюс способность адаптироваться к любому бэкенду,
который у тебя уже есть. (Честное сравнение — в [DESIGN.ru.md](DESIGN.ru.md#позиционирование-честно-vs-beads).)

## Ключевые идеи

- **Исполняемые per-type переходы (killer-фича).** На переход статуса вешаются консольные команды, которые
  обязаны все пройти — `["make lint", "make test"]` как гейт `→ done` — или выполнить действия (создать
  ветку). Definition of Done свой на каждый тип (bugfix/refactor/feature). Агент работает в терминах задач
  (переход-гейт вроде `mtt done`), а дисциплину держит инструмент.
- **Типы и иерархия — из конфига.** Эпик → задача → подзадача — лишь шаблон `hierarchy` (`mtt init --template templates/hierarchy.yaml`); ни имён типов, ни
  структуры ID в коде нет. ID читаемые и **плоские** по префиксу (`e1`, `t17`, `s3`) — стабильны при
  ре-парентинге (иерархия живёт в поле `parent`, а не в ID).
- **Приоритеты, теги, зависимости и роадмап.** `--priority`, `#hashtags` / `--tag`, `depends_on` / `ready` и
  `mtt roadmap` дают агенту упорядоченный фильтруемый бэклог; указатель `current` держит задачу в работе, а
  batch/pipeline (`--ids`, stdin `-`) делает CLI Unix-компонуемым.
- **Гексагон, сменные бэкенды.** Публичный контракт (`pkg/mtt`) с портами `TaskStore` и `KnowledgeStore`;
  YAML-адаптер — референс. Опциональные capability уровня адаптера: история и зависимости — сейчас;
  дерево комментариев и текстовый поиск — планируются.
- **Проверяемые ссылки и append-only история.** Задачи несут проверяемые `refs` на заметки/задачи; каждый
  переход статуса пишется для аудита. (Дерево комментариев — планируется.)
- **Опциональный человеческий UI (`mtt-ui`, планируется).** Маленький локальный веб-сервер (управление задачами, Гант,
  браузер БЗ) — нужен только на YAML-дефолте; при внешнем бэкенде человек использует его родной UI.

## Для агентов

Управление задачами и зависимостями из командной строки и сохранение знаний (`mtt note`) — сейчас; дерево
комментариев, текстовый поиск и опциональный hook внешнего индексатора — планируются.

## Для людей (опционально)

*(Планируется.)* `mtt-ui` (маленький локальный веб-сервер): минималистичное управление задачами, диаграмма
Ганта, браузер БЗ. Плюс CLI — текстовый вывод инфо о задаче, поиска по БЗ и ASCII-Ганта.

## Установка

### Готовый бинарник (рекомендуется)

Скачайте бинарник под свою платформу из
[последнего релиза](https://github.com/pashukhin/mtt/releases/latest):

| Платформа | Файл |
|---|---|
| Linux x86-64 | `mtt_<version>_linux_amd64` |
| Linux ARM64 | `mtt_<version>_linux_arm64` |
| macOS (Intel) | `mtt_<version>_darwin_amd64` |
| macOS (Apple Silicon) | `mtt_<version>_darwin_arm64` |
| Windows x86-64 | `mtt_<version>_windows_amd64.exe` |

Затем, на Unix:

```sh
chmod +x mtt_<version>_<os>_<arch>
sudo mv mtt_<version>_<os>_<arch> /usr/local/bin/mtt
mtt version
```

Проверьте контрольную сумму по `SHA256SUMS` из того же релиза (`sha256sum -c` по строке вашего файла).

### Через Go-тулчейн

```sh
go install github.com/pashukhin/mtt/cmd/mtt@latest
```

### Сборка из исходников

```sh
git clone https://github.com/pashukhin/mtt && cd mtt
make build      # -> bin/mtt
```

## Быстрый старт

```sh
mtt init                    # создать .mtt/ + скаффолд агентских хуков + доков (AGENTS.md/CLAUDE.md/GEMINI.md; --no-agent-hooks/--no-agent-docs чтобы пропустить)
mtt add "Ship auth"         # -> t1 (корневая задача; --parent не нужен)
mtt add "Login endpoint"    # -> t2
mtt status t1 in_progress   # движение по флоу (здесь запускаются + гейтят commands перехода)
mtt done t1                 # -> терминал done (в default-флоу нет gate-команд)
mtt list                    # все задачи
mtt tree                    # дерево задач
mtt roadmap                 # порядок исполнения по зависимостям + приоритетам
# Для иерархии epic > task > subtask: mtt init --template templates/hierarchy.yaml
```

> **Какой флоу?** `default` минимален (task + chore). Для per-type coding-DoD, docs/no-code-петли, иерархии
> epic→task→subtask или полного git-флоу branch→PR→deliver — смотри **галерею примеров** в
> [FLOW_GUIDE.ru.md §2b](FLOW_GUIDE.ru.md#2b-галерея-примеров-флоу-выбери-форму).

Полный список команд и коды выхода — в [CLI_REFERENCE.ru.md](CLI_REFERENCE.ru.md).

> **Существующим проектам:** `mtt init` теперь также пишет `.mtt/.gitignore`, который не пускает
> персональный оверлей `config.local.yaml` в git. Если проект инициализирован раньше, добавьте его
> вручную: `echo config.local.yaml > .mtt/.gitignore`.
